خريطة متقدمة للتصنيفات والمواصفات والفلترة

هذا الملف يشرح كيف تفكر وتُصنّف، وليس فقط ماذا تكتب. الهدف أن تصل إلى نتائج دقيقة عند إضافة منتجات جديدة في Free Zone أو أي مشروع مستقبلي.

التصنيفات

تحدد "مكان" المنتج داخل الشجرة: قسم رئيسي ← قسم فرعي ← نوع فرعي.

المواصفات

تحدد "هوية" المنتج التقنية بقيم معيارية ثابتة وقابلة للمقارنة.

الفلترة

تستخدم المواصفات كـ Facets لإخراج نتائج دقيقة وسريعة ومفهومة للمستخدم.

التدفق المعتمد: تصنيف صحيح → مواصفات صحيحة → فلاتر صحيحة → نتائج شراء أفضل

1) قاعدة القرار الذهبي

إذا اختلف عليك تصنيف منتج، اسأل نفسك: "ما أهم سبب يدفع العميل لشراء هذا المنتج؟".

  • إذا السبب الأساسي هو الحوسبة المحمولة → Laptops
  • إذا السبب الأساسي هو الاتصال والتنقل → Smartphones
  • إذا السبب الأساسي هو العرض البصري → Monitors
  • إذا السبب الأساسي هو التصوير → Cameras

لا تصنّف حسب الوصف التسويقي، صنّف حسب الوظيفة الأساسية للمنتج.

2) شجرة التصنيفات الأساسية

Smartphones Laptops Monitors Cameras Audio Tablets Gaming Networking Storage Printers Smart Home Security & Safety Power & Charging

كل فئة رئيسية يمكن أن تحتوي فئات فرعية، لكن لا تغيّر القاعدة: كل منتج له Category أساسية واحدة فقط.

3) كيف تُصنّف منتج جديد (Workflow عملي)

  1. حدد الفئة الأساسية: category.
  2. حدد الفئة الفرعية: subcategory بدقة (Gaming Laptop / Mirrorless / ...).
  3. استخرج الهوية: brand + model + release_year.
  4. املأ المواصفات: باستخدام مفاتيح معيارية snake_case.
  5. حدد نوع كل خاصية: SELECT / RANGE / BOOLEAN ...
  6. أنشئ variants: عند اختلاف RAM/Storage/Color أو أي خيار شراء فعلي.
  7. اختبر الفلترة: عبر URL مثل ?brand=apple&ram=8,12.

4) مصفوفة أنواع الخصائص (Attributes Types Matrix)

النوع متى نستخدمه مثال خطأ شائع
SELECT عندما القيمة خيار واحد من قائمة resolution = QHD+ كتابة القيمة كنص حر بدون قائمة ثابتة
MULTI_SELECT عندما المنتج يدعم عدة خيارات wifi = Wi-Fi 6, Wi-Fi 7 وضعها SELECT فتفقد خيارات صحيحة
RANGE عندما القيمة رقمية قابلة للمدى battery_capacity = 5000 تخزين الرقم داخل TEXT
BOOLEAN عندما القيمة نعم/لا network_5g = true تخزين yes/no كنصوص غير موحدة
COLOR ألوان الشراء/العرض color = Black خلط اللون مع اسم variant كامل
TEXT وصف تقني غير قابل للتقييس بسهولة screen_protection = Gorilla Glass استخدام TEXT لخصائص كان يمكن فلترتها

4.1) المواصفات الموسعة vs الفلاتر الظاهرة (قاعدة الاعتماد)

المستوى الغرض هل يظهر في الفلاتر؟ قاعدة القرار
Extended Specs عرض تقني كامل + مقارنة تفصيلية ليس دائما يحفظ كل تفاصيل المنتج حتى لو لم تكن مناسبة كفلتر رئيسي
Visible Filters تصفية سريعة للمستخدم نعم subset من المواصفات الموسعة (مشتركة + مهمة للشراء + سهلة الفهم)

عمليا: الفلاتر الظاهرة تبنى من الجزء المشترك والمهم فقط من المواصفات الموسعة، وليس من كل الحقول.

5) أمثلة Facets قوية حسب الفئة

الفئة أهم مفاتيح الفلترة أمثلة URL
Smartphones brand, ram, storage, chipset, network_5g, battery_capacity, refresh_rate ?brand=apple,samsung&ram=8,12&network_5g=true&price=400-1200
Laptops processor_family, ram_size, storage_type, gpu_model, screen_size, refresh_rate ?processor_family=Core i7,Ryzen 7&ram_size=16,32&gpu_model=RTX 4060
Monitors panel_type, resolution, refresh_rate, size_inch, hdr, response_time_ms ?panel_type=IPS,OLED&refresh_rate=120-240&size_inch=27-34
Cameras camera_type, sensor_type, resolution_mp, ibis, max_video_resolution, mount ?camera_type=Mirrorless&sensor_type=Full-Frame&ibis=true

6) أخطاء تسبب نتائج سيئة

  • إدخال RAM كـ eight بدل 8
  • تكرار نفس المعنى بمفتاحين مختلفين
  • اختيار Category خاطئة للمنتج
  • عدم توحيد الوحدات (GB, inch, Hz...)

7) قواعد جودة البيانات

  • مسموح: ram_size, battery_capacity
  • مرفوض: مفاتيح عشوائية مثل myRamField
  • كل رقم يجب أن يكون رقما فعليا وليس نصا
  • القيم الفارغة تسجل null وليس تخمينا

8) هدفك النهائي

  • المستخدم يجد المنتج بسرعة
  • المقارنة بين المنتجات تكون عادلة
  • صفحات الفئة تبقى نظيفة حتى مع آلاف المنتجات
  • إضافة فئة جديدة بدون كسر النظام

9) مثال كامل من الإدخال إلى الفلترة

مثال: Laptop Gaming جديد
  • Category: Laptops
  • Subcategory: Gaming Laptops
  • Brand/Model: ASUS / ROG Strix G16
  • Attributes: processor_family=Core i7, ram_size=16, storage_type=SSD NVMe, gpu_model=RTX 4060, refresh_rate=165, screen_size=16
  • URL Filter test: ?processor_family=Core i7&ram_size=16&gpu_model=RTX 4060&refresh_rate=144-240

10) Checklist قبل اعتماد أي تصنيف

  • [ ] هل category صحيحة 100%؟
  • [ ] هل subcategory أدق خيار متاح؟
  • [ ] هل attributes الأساسية مكتملة؟
  • [ ] هل النوع لكل attribute صحيح؟
  • [ ] هل الوحدات موحدة؟
  • [ ] هل اختبرت فلترة URL وظهرت نتائج منطقية؟

إذا جاوبت "نعم" على كل النقاط، غالبا التصنيف جاهز للاعتماد ويعطي نتائج ممتازة.

11) ربط Admin Panel بواجهة المستخدم (الجزء الأهم تشغيليا)

ما يتم في Admin أين يحفظ في النظام أثره المباشر في واجهة المستخدم
إنشاء فئة رئيسية/فرعية Category ظهور صفحة فئة ومسار واضح للمنتجات
تعريف خصائص الفئة CategoryAttribute توليد الفلاتر ديناميكيا في Sidebar
إضافة المنتج الأساسي Product ظهور بطاقة المنتج في نتائج الفئة
إدخال قيم المواصفات ProductAttributeValue دخول المنتج فعليا في نتائج الفلترة
إضافة خيارات شراء (رام/تخزين/لون) ProductVariant اختيارات شراء دقيقة في صفحة المنتج

القاعدة: إذا لم تُدخل المواصفات بشكل صحيح في Admin، فالفلترة في الواجهة لن تكون منطقية حتى لو التصميم ممتاز.

12) التشغيل اليومي المقترح (Daily Workflow)

  1. مراجعة المنتجات الجديدة المطلوب إضافتها اليوم.
  2. التأكد أن الفئة وخصائصها موجودة قبل إدخال المنتج.
  3. إدخال المنتج + المواصفات + variants.
  4. اختبار فلاتر URL للفئة بعد الإضافة مباشرة.
  5. تسجيل أي key جديد في دليل التصنيف لمنع العشوائية.

13) توزيع المسؤوليات داخل الفريق

  • Admin Manager: إدارة taxonomy وattribute schemas.
  • Catalog Operator: إدخال المنتجات والمواصفات اليومية.
  • QA: اختبار ظهور المنتج وصحة نتائج الفلاتر.
  • Frontend: عرض الفلاتر والنتائج فقط (بدون hardcode).
  • Backend: ضمان صحة التخزين والتحقق والindexes.

هذا الفصل بين الأدوار يمنع تضارب القرارات ويحافظ على منطق ثابت مع نمو عدد المنتجات.

14) سيناريو تحقق سريع بعد أي تحديث Admin

  • 1) افتح صفحة الفئة (مثال: /c/smartphones).
  • 2) تأكد أن الفلتر الجديد ظاهر بالاسم الصحيح.
  • 3) فعّل الفلتر وتحقق من عدد النتائج.
  • 4) انسخ URL وأعد فتحه في تبويب جديد للتأكد من ثبات الحالة.
  • 5) إذا ظهرت نتائج غير منطقية: راجع نوع الحقل وقيمه في Admin.
