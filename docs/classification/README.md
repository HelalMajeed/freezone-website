# Free Zone Classification README

مرجع تشغيلي مختصر يربط بين **Admin Panel** و**واجهة المستخدم** ويشرح طريقة العمل اليومية بمنطق واضح.

---

## 1) الفكرة الأساسية

النظام يعمل كخط إنتاج بيانات:

`Admin Data Entry -> Validation -> Database (Category/Attributes/Values) -> User Filters -> Better Results`

إذا كان الإدخال في لوحة الإدارة صحيحا، واجهة المستخدم ستعطي نتائج دقيقة تلقائيا.

---

## 2) نموذج الربط بين الادمن والواجهة

### داخل Admin Panel
- إدارة الشجرة: `Category` و `Subcategory`
- إدارة القوالب: `CategoryAttribute`
- إدخال المنتجات: `Product`
- إدخال قيم المواصفات: `ProductAttributeValue`
- إدارة Variants: رام/تخزين/لون/سعر/مخزون

### داخل واجهة المستخدم
- صفحة الفئة تقرأ خصائصها من `CategoryAttribute`
- الفلاتر تتولد تلقائيا حسب النوع (`SELECT`, `RANGE`, ...)
- النتائج تتصفى من `ProductAttributeValue`
- URL يمثل حالة الفلاتر (للمشاركة/الحفظ)

---

## 3) دورة العمل اليومية (Daily Operations)

1. مدير المحتوى يضيف فئة جديدة أو يحدث فئة موجودة.
2. مدير البيانات يضيف/يعدل `CategoryAttribute` للفئة.
3. فريق المنتجات يدخل المنتج مع مواصفاته وقيمه الفعلية.
4. النظام يتحقق من صحة الأنواع والوحدات.
5. المنتج يظهر في الواجهة.
6. الفلاتر تعمل فورا على المنتج الجديد بدون تعديل كود يدوي.

---

## 4) قواعد الإدخال داخل Admin (إلزامية)

- لا Attribute بدون نوع واضح.
- لا مفتاح عشوائي: استخدم `snake_case`.
- الوحدات موحدة لكل فئة (`GB`, `inch`, `Hz`, `mAh`, `W`, `MP`).
- القيم الرقمية تدخل كأرقام وليس نصوص.
- الخصائص المهمة للفلترة تكون `filterable = true`.
- أي بيانات غير مؤكدة تسجل `null` وليس تخمين.

---

## 5) أنواع الخصائص وكيف تنعكس على الواجهة

- `SELECT` -> قائمة اختيار مفرد
- `MULTI_SELECT` -> عدة خيارات
- `RANGE` -> Min/Max
- `BOOLEAN` -> نعم/لا
- `COLOR` -> دوائر ألوان
- `TEXT` -> للعرض غالبا وليس للفلترة الثقيلة

---

## 6) قاعدة "المواصفات الموسعة" مقابل "الفلاتر الظاهرة"

- **المواصفات الموسعة (Extended Specs):** كل تفاصيل المنتج التقنية للعرض والمقارنة.
- **الفلاتر الظاهرة (Visible Filters):** جزء منتقى من المواصفات الموسعة فقط.

قاعدة الاعتماد:
- إذا الخاصية مشتركة بين أغلب منتجات الفئة وتؤثر على قرار الشراء -> `filterable = true`
- إذا الخاصية تفصيلية/نادرة/صعبة على المستخدم -> تبقى في المواصفات فقط `filterable = false`

النتيجة:
- واجهة فلترة واضحة وغير مزدحمة
- نتائج أدق
- قابلية توسع أفضل

---

## 7) أمثلة عملية URL (واجهة المستخدم)

- `?brand=apple,samsung`
- `?price=300-1200`
- `?ram=8,12`
- `?network_5g=true`
- `?processor_family=Core i7,Ryzen 7&ram_size=16,32`

---

## 8) أمثلة المواصفات لكل فئة

### Smartphones
brand, model, chipset, ram, storage, screen_size, refresh_rate, battery_capacity, network_5g

### Laptops
processor_family, ram_size, storage_type, gpu_model, screen_size, refresh_rate, battery_wh, weight

### Monitors
panel_type, resolution, refresh_rate, response_time_ms, hdr, size_inch

### Cameras
camera_type, sensor_type, resolution_mp, ibis, max_video_resolution, mount

---

## 9) الأخطاء التي تكسر المنطق

- تصنيف المنتج في Category خاطئة
- تكرار نفس المفهوم بأكثر من key
- استخدام TEXT بدل RANGE للقيم الرقمية
- عدم توحيد الوحدات
- إدخال قيم Variants بلا ارتباط بالمواصفات الأساسية

---

- [ ] المنتج يظهر في صفحة الفئة الصحيحة
- [ ] فلاتر URL ترجع نتائج منطقية

---

## 11) كيف تعتمد الملف في الفريق

اعتمد هذا الملف كمرجع موحد بين:
- فريق الإدارة (إدخال البيانات)
- فريق الواجهة (عرض وفلاتر)
- فريق الجودة (التحقق والتدقيق)

أي تعديل في التصنيف يبدأ من Admin Schema ويجب أن يمر عبر هذا المرجع قبل اعتماده.
